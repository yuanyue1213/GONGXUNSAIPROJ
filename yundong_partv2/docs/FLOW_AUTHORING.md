# 全流程编写约定

当前 STM32 参数的唯一编辑入口是 `App/Inc/robot_config.h`。旧 `motion_speed.h`、`mission_config.h` 仅转发包含，不再保存参数；区域姿态参数也从 `arm_flow.h` 移到了统一配置头。

本约定对应当前顺序执行版本。普通路线修改只编辑 `stm32/yundongv2/App/Inc/mission_flow.h` 的 `mission_flow[]`，修改后重新编译、烧录 STM32。App 只负责启动，ESP32 只负责转发。

## 1. 流程怎样执行

`mission_flow[]` 是编译进固件的动作数组。STM32 启动任务时先用 `Flow_Check()` 检查整张表，通过后按数组顺序逐条调用动作函数。

- 一行表示一个流程步骤；上一动作函数返回后，才执行下一步。
- 多轴并行由动作函数内部完成，表中仍按步骤顺序书写。
- 当前每步执行成功后额外等待 100 ms；`FLOW_END()` 直接结束。
- `.h` 文件不是运行时脚本。数组内不能写 `if`、`for`、`while`、`HAL_Delay()` 或函数调用语句，也不能从 App 临时修改。
- 只能使用本文列出的 `FLOW_*` 操作。需要新动作时，要同时扩展数据定义、校验和执行代码，见第 9 节。

## 2. 文件和书写格式

保留现有文件的头文件保护、`#include "flow_types.h"` 和数组名称：

```c
static const FlowStep mission_flow[] = {
    FLOW_PREPARE(),
    FLOW_IMU_ZERO(),
    FLOW_STOW(),

    /* 第一段：到达目标区域。 */
    FLOW_MOVE(FLOW_FORWARD, 500),

    FLOW_STOW(),
    FLOW_END(),
};
```

书写约定：

1. 每行一个操作，缩进四个空格，行尾加逗号；数组末尾使用 `};`。
2. 参数使用整数常量，不写小数、负数或单位后缀。例如写 `500`，不写 `0.5`、`-500`、`500mm`。
3. 方向和批次使用命名常量，不直接写 `'F'`、`'L'`、`1`、`2`。
4. 按“出发、扫码、原料区、加工区、暂存区、返回”等实际任务分段，用中文注释说明目的。
5. 路线注释编号只是方便阅读，不控制执行。数组顺序才决定执行顺序。

## 3. 支持的操作

| 写法 | 含义 | 参数约定 |
|---|---|---|
| `FLOW_PREPARE()` | 初始化舵机输出姿态 | 必须是第一步，且只出现一次 |
| `FLOW_IMU_ZERO()` | 将当前航向记录为转向参考 | 仅转向前必须建立；允许车体静止时重新建立参考 |
| `FLOW_STOW()` | 抬到行走高度、收臂、底座回180°行走角、转盘回零 | 按需使用；建议起步、离开站点和结束前使用 |
| `FLOW_MOVE(方向, 距离)` | 沿车体方向平移 | 距离为 **1～10000 mm** 的整数 |
| `FLOW_TURN(方向, 角度)` | 修改目标航向并转向 | 只支持左、右；角度为 **1～360 度** 的整数 |
| `FLOW_SCAN_TASK()` | 从相机读取任务二维码 | 物料站点操作之前必须扫码；允许重新扫码更新任务码 |
| `FLOW_PICK_RAW(批次)` | 从原料区取三件物料，转移到车载槽位 | 第一批或第二批 |
| `FLOW_PROCESS_PUT(批次)` | 将该批三件物料从车载槽位放入加工区 | 第一批或第二批；自行安排物料来源 |
| `FLOW_PROCESS_GET(批次)` | 将该批三件物料从加工区取回车载槽位 | 第一批或第二批 |
| `FLOW_STORE(批次)` | 将该批三件物料放入暂存区 | 第一批或第二批 |
| `FLOW_STACK(批次)` | 将该批三件物料放到码垛位置 | 第一批或第二批 |
| `FLOW_ARM(动作组)` | 执行自定义机械臂和舵机动作 | 完整执行后继续总流程，可重复引用 |
| `FLOW_END()` | 结束任务，发布完成状态 | 必须是最后一步，且只出现一次 |

完整流程总长度为 **2～128 步**，最小合法表是 `PREPARE → END`。只有转向依赖 IMU 参考；直线移动、机械臂、收臂和扫码无需 IMU。使用二维码的物料站点仍须先扫码。

`FLOW_PREPARE()` 当前设置夹爪 15°、转盘 0°、底座 90°。它不会寻找限位、读取编码器回零或自动收拢机械臂。`FLOW_STOW()` 才负责机械臂收拢，且不会重设夹爪角度。

## 4. 方向和单位

| 常量 | 移动含义 | 转向含义 |
|---|---|---|
| `FLOW_FORWARD` | 车体向前 | 不支持 |
| `FLOW_BACKWARD` | 车体向后 | 不支持 |
| `FLOW_LEFT` | 车体向左横移 | 向左转 |
| `FLOW_RIGHT` | 车体向右横移 | 向右转 |

方向以**车体当前朝向**为准，不是场地固定的东、西、南、北。车转向后，下一次 `FLOW_FORWARD` 沿新的车头方向移动。

```c
FLOW_MOVE(FLOW_FORWARD, 1000),  // 前进 1000 mm，即 1 m。
FLOW_TURN(FLOW_LEFT, 90),       // 向左转 90°，不是指定绝对航向。
FLOW_MOVE(FLOW_FORWARD, 500),   // 沿转向后的车头方向前进 500 mm。
FLOW_MOVE(FLOW_BACKWARD, 200),  // 后退 200 mm，不写负距离。
```

左右转是在已记录的目标航向上累计转向量，不是给定场地绝对角度。`FLOW_IMU_ZERO()` 应在车体静止时执行；再次调用会以当时的实测航向替换原参考，后续转向从新参考累计。

流程宏只指定距离、角度和批次，不带速度参数。默认速度在 `motion_speed.h`，距离换算和图像方向标定在 `mission_config.h`。不要为了改变速度而修改流程距离。

## 5. 物料操作的自由编排

校验器不再绑定比赛顺序。下面是默认比赛路线采用的顺序示例，可以根据现场物料状态修改：

```text
扫码
  ↓
第一批：原料抓取 → 加工放置 → 加工取回 → 暂存
  ↓
第二批：原料抓取 → 加工放置 → 加工取回 → 码垛
```

以下只展示站点先后关系，**不是可直接用于实车的路线**；实际必须在相应操作之间补充导航和收臂步骤：

```c
FLOW_SCAN_TASK(),

/* 先导航到原料区。 */
FLOW_PICK_RAW(FLOW_BATCH_1),
/* 收臂，导航到加工区。 */
FLOW_PROCESS_PUT(FLOW_BATCH_1),
FLOW_PROCESS_GET(FLOW_BATCH_1),
/* 收臂，导航到暂存区。 */
FLOW_STORE(FLOW_BATCH_1),

/* 收臂，返回原料区。 */
FLOW_PICK_RAW(FLOW_BATCH_2),
/* 收臂，导航到加工区。 */
FLOW_PROCESS_PUT(FLOW_BATCH_2),
FLOW_PROCESS_GET(FLOW_BATCH_2),
/* 收臂，导航到码垛区。 */
FLOW_STACK(FLOW_BATCH_2),
```

具体规则：

- 每个站点操作自动处理该批的三件物料，不要为每一件重复写同一个站点操作。
- `PROCESS_PUT` 与 `PROCESS_GET` 分开：先放完三件，再取回三件。
- 可以先执行第二批、交错批次、重复站点，也可以执行部分操作后结束。
- STORE 和 STACK 都接受第一批或第二批，不限制批次用途。
- 允许只写移动或自定义动作组，不需要扫码；使用物料站点时仍须先扫码。
- 校验器不跟踪实际装载状态；放置前槽位中是否有料、取料位置是否有料，由编写者保证。

二维码格式为 `三位颜色+三位位置+三位颜色+三位位置`，例如 `156+123+516+231`。每批颜色编号为 1～6 且互不重复，两批使用相同颜色集合；位置编号为 1～3 且每批互不重复。当前没有预置任务码或跳过扫码模式。

## 6. 站点操作的边界

**到工位由你写路线，工位内的对准和取放由站点函数完成。**

- `PICK_RAW`、`PROCESS_PUT`、`PROCESS_GET`、`STORE`、`STACK` 只处理三件物料，不再自动对准。需要对准时，在前面显式插入 `FLOW_ALIGN(视觉模式,批次)`，任务后收臂，再执行 `FLOW_UNALIGN()` 返回校准前的位置，见 [视觉校准与撤销](VISION_ALIGNMENT.md)。
- 视觉对准采用参考项目的粗调搜索和两次修正：粗调收到明确 NONE 时，按前移 100 → 后移 100 → 左移 50 → 右移 50 mm 循环，每段结束都重新识别；找到目标立即停止搜索；取得坐标后计算 X/Y 位移，按先前后、后左右的顺序移动完成粗调；再重新识别一帧，依次移动完成精调，随后进入取放。没有循环到 1 像素的条件，也没有单轴 25 mm 截断。它不会自动寻找远处工位或规划路线，流程必须先将车开到正确工位附近。
- 原料抓取固定使用近端中间姿态，等待相机 `NEAR` 结果后夹取；加工取回和码垛使用 `PICK` 结果选择物理位置。
- 离开站点前建议显式写 `FLOW_STOW()`。站点动作结束不等于机械臂已经完全收回行走姿态。
- `PROCESS_PUT` 与 `PROCESS_GET` 在同一加工区，二者之间是否需要等待、移动，必须按实际任务安排。当前宏集合没有单独的延时操作。
- 搜索参数位于 `mission_config.h`：前后每段 100 mm、左右每段 50 mm，每个站点从前移开始，按前、后、左、右循环；每段后先重新识别，找到后不再执行剩余搜索动作；每轮结束停在起点右侧50 mm，下一轮仍使用原起点，不扩大范围；每次请求有 1500 ms 稳定识别窗口，随后收到新的 NONE 才搜索。搜索没有次数上限，路线应先将车开到正确工位附近。

物理左/中/右位置在 `arm_flow.h` 的 `ARM_STATION_POSES` 中定义。车载槽位的转盘角为 0°、120°、240°，不等于物理工位编号。普通路线编写无需修改这些取放参数；修改机械臂和舵机动作见 [机械臂动作编写](ARM_FLOW.md)。

## 7. 可直接替换的简单路线示例

保留现有头文件保护和 include，只替换数组：

```c
static const FlowStep mission_flow[] = {
    FLOW_PREPARE(),
    FLOW_IMU_ZERO(),
    FLOW_STOW(),

    /* 第一段：前进。 */
    FLOW_MOVE(FLOW_FORWARD, 500),

    /* 第二段：转向后继续前进。 */
    FLOW_TURN(FLOW_LEFT, 90),
    FLOW_MOVE(FLOW_FORWARD, 300),

    /* 第三段：横移到终点附近。 */
    FLOW_MOVE(FLOW_RIGHT, 200),

    FLOW_STOW(),
    FLOW_END(),
};
```

这张表不包含扫码和取放，执行结束时车不会自动返回起点。如果需要返回，必须显式写出返回路线。现有 `mission_flow.h` 则是完整比赛路线的参考。

## 8. 校验与执行边界

启动时若校验失败，App 会收到 `ERROR` 和对应原因，本轮不会开始执行流程。

| 原因 | 检查内容 |
|---|---|
| `FLOW_LENGTH` | 步数不在 2～128 范围内，或表为空 |
| `FLOW_BOUNDARY` | 第一项不是 PREPARE，或最后一项不是 END |
| `FLOW_PREPARE` | PREPARE 出现在中间 |
| `FLOW_REFERENCE` | 转向前没有建立航向参考 |
| `FLOW_DIRECTION` | 移动方向无效，或转向使用了前/后方向 |
| `FLOW_DISTANCE` | 移动距离为 0 或超过 10000 mm |
| `FLOW_ANGLE` | 转角为 0 或超过 360° |
| `FLOW_TASK_CODE` | 物料操作前没有扫码 |
| `FLOW_ARM_GROUP` | 自定义动作组为空或长度不在 1～128 范围 |
| `FLOW_END` | END 提前出现 |
| `FLOW_PARAMETERS` | 手写结构体填入了当前操作不应携带的字段 |
| `FLOW_OPCODE` | 操作类型未知 |

校验只检查动作格式、方向/距离/角度、动作组长度，以及转向前的参考和物料站点前的扫码，不读取批次字段、不限制比赛站点顺序，也不验证车是否真的到达工位、路线是否碰撞或机械臂是否可达。站点宏仍用第一批或第二批选择二维码数据；执行站点时只保留数组越界保护，越界则按动作失败退出。收臂等建议不会由校验器自动补上。

当前执行方式也应纳入流程安排：

- 步进位置动作按预计耗时推进，多轴等待预计耗时的最大值；没有实际到位轮询。
- 转向等待 IMU 角度稳定；视觉粗调在识别窗口后收到 NONE 时进行搜索，无回复仍等待；精调等待有效坐标。两者没有总等待超时。精调移动完成后不再复查像素误差。
- `FLOW_END()` 不会自动收臂、回到起点或代替急停。
- 启动前将机械臂放到约定初始姿态。上电姿态视为逻辑零点，PREPARE 不会自动机械回零。

## 9. 修改、验证和扩展

自定义机械臂和舵机动作组无需新增流程操作：在 `arm_flow.h` 定义 `static const ArmStep my_action[]`，然后在总流程用 `FLOW_ARM(my_action)` 引用。该组完整执行后才进入下一步，可重复引用。具体写法见 [机械臂动作编写](ARM_FLOW.md)。空指针、空组或超过 128 步返回 `FLOW_ARM_GROUP`，不要求 IMU_ZERO。该操作不自动扫码、对准或计入批次取放。

普通路线修改步骤：

1. 在纸面上确定起始朝向、工位位置以及每段移动后的车头方向。
2. 修改 `mission_flow[]`，检查距离单位、批次和工位之间的导航。
3. 在 STM32 工程目录执行 `cmake --preset Debug`、`cmake --build --preset Debug`。
4. 烧录新固件，按修改后的路线进行实车验证。

当前 `tests/run_tests.py` 的部分回归测试绑定原比赛路线的 25 个路线动作、8 个站点和 24 次取放。改变默认路线后，应同步调整相关预期；测试次数不匹配不等于新流程格式非法。格式和顺序以 `Flow_Check()` 的实际检查为准。

需要加入本文未列出的操作时，修改以下位置：

| 文件 | 修改内容 |
|---|---|
| `App/Inc/flow_types.h` | 添加操作类型、需要的数据字段和初始化宏 |
| `App/Src/flow_check.c` | 添加参数和必要前置条件校验 |
| `App/Src/mission_runner.c` | 在顺序 switch 中执行新操作 |
| `App/Src/motion_control.c` 或对应驱动 | 仅在现有动作函数不足时扩展底层动作 |
| `tests/` 与本约定 | 更新相应行为验证和使用说明 |

只在 `mission_flow.h` 写一个新的宏名称，不会自动增加动作能力。
